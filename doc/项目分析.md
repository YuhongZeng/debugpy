# debugpy 项目分析

本文是对本仓库（`YuhongZeng/debugpy`）的架构与现状总结，基于源码、文档、测试与 git 历史整理。上游仓库为 [microsoft/debugpy](https://github.com/microsoft/debugpy)。

---

## 1. 项目定位

debugpy 是 Python 的 [Debug Adapter Protocol (DAP)](https://microsoft.github.io/debug-adapter-protocol/) 实现，给 IDE 提供标准调试能力，本身不包含调试 UI。

它被 VS Code Python 扩展、Visual Studio 等作为 Python 调试后端使用，属于生产级项目（PyPI classifier: Production/Stable），许可证为 MIT。

职责可以分成两层：

- **协议层**：对 IDE 暴露 DAP（launch / attach、断点、单步、求值、线程等）。
- **调试内核**：内嵌 vendored 的 [PyDev.Debugger (`pydevd`)](https://github.com/fabioz/PyDev.Debugger)，负责真正的追踪、挂起、表达式求值。

使用入口有两种：

```console
python -m debugpy --listen 5678 --wait-for-client script.py
```

```python
import debugpy
debugpy.listen(5678)
debugpy.wait_for_client()
```

当前仓库要求 **Python >= 3.8**。tox 覆盖 3.8–3.12，Azure Pipelines 目前测到 3.11。`CONTRIBUTING.md` 里仍提到 Python 2.7 / 3.5，已经过时。

## 3. 进程架构

一次调试会话通常涉及三类角色：

```
IDE (VS Code / 其他 DAP client)
        │  DAP over stdio 或 TCP
        ▼
debugpy adapter   ← 独立进程：中转消息、管理会话、处理子进程调试
        │  DAP / 自定义协议
        ▼
debuggee + pydevd ← 被调试进程内部的 debug server
```

术语（见 `doc/Subprocess debugging.md`）：

- **Debuggee**：被调试的用户进程。
- **Debug server**：debuggee 内的 pydevd + debugpy 包装。
- **Debug adapter**：独立的 debugpy adapter，夹在 IDE 与 server 之间。

两种主场景：

1. **launch**：IDE 拉起 adapter → adapter 拉起 debuggee → 双向 DAP。
2. **attach**：用户先 `debugpy.listen()`，IDE 再连上；断线后 TCP 连接可保持，便于重连。

`listen()` 默认会再 spawn 一个 adapter 进程，并用随机 access token 互认。`in_process_debug_adapter=True` 时不拆进程，但子进程调试会失效。

子进程调试依赖 adapter 的 server listener：第一个连接视为根进程，之后都是 subprocess，并通过 `ptvsd_subprocess` 事件通知 IDE。

## 4. 源码结构

包采用 src layout：`src/debugpy/`。debugpy 自有 Python 代码约 7700 行；体积和复杂度主要在 vendored `pydevd`。

```
src/debugpy/
├── __init__.py / public_api.py   # 稳定公开 API（延迟加载 server）
├── __main__.py                   # python -m debugpy / 直接执行入口
├── adapter/                      # 独立 adapter 进程
│   ├── clients.py                # IDE 侧 DAP
│   ├── servers.py                # debug server 连接
│   ├── sessions.py               # 会话生命周期
│   ├── launchers.py              # launch 场景
│   └── __main__.py
├── server/                       # 跑在 debuggee 内
│   ├── api.py                    # listen / connect / wait_for_client 实现
│   ├── cli.py                    # 命令行解析与启动
│   └── attach_pid_injected.py    # --pid 注入
├── launcher/                     # 拉起 debuggee、转发 stdio
├── common/                       # DAP JSON 通道、日志、socket
│   └── messaging.py              # 最重的自有模块（约 1500 行）
└── _vendored/pydevd/             # 调试内核（Cython 加速、attach-to-process 等）
```

对应职责：

| 包 | 职责 |
|---|---|
| `public_api.py` | 对外稳定 API；调用时才 import server，避免污染 adapter |
| `adapter/` | 独立 adapter：client / server / launcher / session |
| `server/` | debuggee 侧：CLI、listen/connect、PID attach |
| `launcher/` | launch 场景：启动 debuggee、转发输出 |
| `common/` | DAP 消息通道、日志、socket |
| `_vendored/pydevd/` | 真正的追踪与调试引擎 |

打包用 setuptools + versioneer。wheel 标成 non-pure：会尽量编译 pydevd 的 Cython 扩展，失败可降级为纯 Python（`REQUIRE_CYTHON_BUILD=1` 时强制失败）。

## 5. 公开 API 与 CLI

稳定 API 只暴露这些符号（见 `src/debugpy/__init__.py` 的 `__all__`）：

```python
debugpy.listen(5678)              # 或 (host, port)
debugpy.connect(...)              # 连接到已有 adapter
debugpy.wait_for_client()         # 阻塞直到客户端连上；可 cancel
debugpy.is_client_connected()
debugpy.breakpoint()              # 同时挂到 builtins.breakpoint
debugpy.configure(subProcess=False, qt="none", ...)
debugpy.debug_this_thread()       # 非 threading 模块启动的线程需要显式注册
debugpy.trace_this_thread(False)  # 关闭当前线程追踪
debugpy.log_to("/path")
```

CLI 对应关系：

| CLI | 含义 |
|---|---|
| `--listen [<host>:]<port>` | 监听 IDE 连接 |
| `--connect [<host>:]<port>` | 连接到已有 adapter |
| `--wait-for-client` | 等客户端连上再跑用户代码 |
| `--pid <pid>` | 注入正在运行的 Python 进程 |
| `--configure-<name> <value>` | 早期配置（如 `subProcess`） |
| `--log-to <path>` | 内部日志目录 |

也可用环境变量 `DEBUGPY_LOG_DIR` 开启日志。

## 6. 测试与工程化

测试以 DAP 端到端为主，而不是大量单元测试。核心脚手架：

- `tests/debug/session.py`：完整会话生命周期（launch → breakpoint → continue → disconnect）
- `tests/timeline.py`：按时间线断言 DAP 消息顺序
- `tests/debugpy/test_*.py`：覆盖断点、单步、attach、多进程、Django/Flask、gevent、path mapping、justMyCode、completions、evaluate 等

工具链：

| 项 | 选择 |
|---|---|
| 测试 | pytest + xdist（`-n8`）+ timeout 30s |
| 覆盖率 | pytest-cov + `.coveragerc` |
| Lint | Ruff（CI 失败即阻断） |
| 格式 | Black |
| 类型检查 | Pyright（target 3.8） |
| 本地全量 | tox：`py{38,39,310,311,312}{,-cov}` |

CI 在 Azure Pipelines：Linux / macOS / Windows × Python 3.8–3.11，另有分平台 coverage pipeline。GitHub Actions 只跑 CodeQL 和 stale。

测试依赖见 `tests/requirements.txt`：pytest 系列、psutil，以及被调试代码用的 django / flask / gevent / requests。

## 7. 本 fork 的 `multiThread` 改动

默认 DAP 行为是「一处断点，所有线程一起停」。本 fork 增加 `multiThread: true`，改为按线程暂停。

涉及文件：

- `src/debugpy/adapter/clients.py`
- `src/debugpy/_vendored/pydevd/pydevd.py`
- `src/debugpy/_vendored/pydevd/_pydevd_bundle/pydevd_api.py`
- `src/debugpy/_vendored/pydevd/_pydevd_bundle/pydevd_json_debug_options.py`
- `src/debugpy/_vendored/pydevd/_pydevd_bundle/pydevd_process_net_command_json.py`
- `src/debugpy/_vendored/pydevd/_pydevd_bundle/pydevd_net_command_factory_json.py`
- `src/debugpy/_vendored/pydevd/_pydevd_bundle/pydevd_net_command_factory_xml.py`

行为变化：

| 点 | 默认 | `multiThread: true` |
|---|---|---|
| 断点 `suspend_policy` | `ALL` | `NONE` |
| `pause` / `continue` 的 `threadId` | 强制改成 `*` | 保持客户端传入值 |
| `stopped` / `continued` 事件 | `allThreadsStopped/Continued=True` | 按线程报告 |
| `steppingResumesAllThreads` | 默认 true | 关闭 |

适用场景：服务端多线程、GUI 事件循环等「只停当前线程、其它线程继续跑」的需求。

尚未产品化的地方：

1. 直接改了 vendored pydevd，以后 sync 上游容易冲突。
2. 没有对应测试、文档，也没有 `debugpy.configure()` / CLI 入口；目前只能通过 launch/attach 参数 `multiThread` 开启。
3. `DEBUG_OPTIONS_BY_FLAG` 中 `MultiThread: MULTI_THREAD=False` 看起来像笔误（flag 名却映射成 False）。
4. 与上游脱节，后续维护成本高。

## 8. 总体判断

| 维度 | 判断 |
|---|---|
| 成熟度 | 生产级，VS Code Python 调试的事实标准 |
| 架构 | adapter / server / launcher 三层清晰，内核是 pydevd |
| 复杂度 | debugpy 包装层中等；难点在 pydevd 与 DAP 时序 |
| 本仓库 | 上游快照 + 一个未完全产品化的 `multiThread` 补丁 |
| 维护风险 | vendored 内核分叉、文档/测试滞后、与上游脱节 |

---

## 9. 建议后续方向

按优先级：

1. **给 `multiThread` 补测试与文档**  
   至少覆盖：单线程断点不停其它线程、continue 只恢复当前线程、step 不 resume all。并在 README / wiki 说明 launch.json 用法。

2. **修掉配置笔误，补齐入口**  
   视需求把选项接到 `debugpy.configure()` 和 `--configure-multiThread`。

3. **减少对 vendored pydevd 的侵入**  
   能放在 adapter 层的逻辑尽量上移；必须改 pydevd 时单独记录补丁，方便 rebase。

4. **评估是否 rebase 上游**  
   若还要长期维护本 fork，应对照最新 `microsoft/debugpy` 做差异分析后再合入，否则安全修复和 Python 新版本支持都会落后。

5. **更新过时文档**  
   `CONTRIBUTING.md` 的 Python 2.7 / Flake8 描述应与当前 Ruff + 3.8+ 现状对齐。
